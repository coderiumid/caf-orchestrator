## T1 Audit (read-only, before any `src/` change)

Verdict: no AC contradicted; A1, A3 and A4 hold with the changes the spec itself anticipates, A2 does not hold as-is and needs two minimal new read methods (the spec allows that). No STOP.

- **A1 (label in payload)**: GitHub — `issues` `labeled` carries `issue.labels[]` (the DTO already `.passthrough()`s `issue`); Linear — the `Issue` update payload's `data` carries `labels: [{id,name,color}]` (also passthrough). Both are read with `labelNames()` in `routes/webhooks.ts`; no port needed. **Not verifiable offline**: no real Linear payload fixture exists in this repo; an absent/odd `labels` field reads as "no labels" (gate off, never a crash). Caveat: the label set is the one at the moment the ready trigger fires — a gate label added afterwards does not gate an already-queued run.
- **A2 (read ticket comments)**: **not available** — `ILinearClient` had `postComment`/`updateStatus` only; `IVcsClient` had no comment read (`GithubService.listIssueComments` exists but is off-port, returns only `{id, body}` and is used by the PR-review route). Added the minimal pair: `ILinearClient.listComments(ticketId)` (GraphQL `issue.comments`, includes `botActor`) and `IVcsClient.listTicketComments({owner, repo, issueNumber})`, both returning `TicketComment {id, body, authorIsBot, createdAt?}` oldest first. The orchestrator's own comments are not recognisable by author (same API key/PAT as a human), so the Clarify comment starts with the marker `❓ CAF-CLARIFY` and "after the last Clarify comment" means after the last comment containing it.
- **A3 (pipeline on an existing branch)**: the normal path is `clone baseBranch` → `createBranch ai-agent/<KEY>` (`git checkout -b`), so it **fails or recreates** on an existing branch — and a pushed Clarify draft puts the branch on the remote. The Linear webhook already diverts "branch exists" to the `isRetry` resume path; the GitHub `issues` webhook did not. Change made: the GitHub trigger does the same check (`githubService.branchExists`) and enqueues `isRetry: true`, and the use case branches on `orchestration-state.json` before the retry budget. The normal path is untouched (detecting the branch there would have changed every existing test, whose `remoteBranchExists` mock defaults to `true`).
- **A4 (state shape)**: `OrchestrationState` is plain JSON read by `readOrchestrationState` (`JSON.parse`, no schema); the dashboard watcher only keys on the file. An optional `waitingFor?: 'clarify' | 'spec-approval'` reads fine from old files (test in `orchestration-state.sdd04c.test.ts`). `recordGateFailure` builds a fresh object, so a later gate failure drops the marker; `incrementOrchestrationRetryCount` likewise.
- **Point after planner / before implementation**: `execute()` non-retry branch, between the planner run and `readTasks` — now `planTicket()` (shared by a new ticket and a Clarify resume). The check sits **before** `tasks.md` is required, since a planner that stops for clarification may write none.
- **PR creation/update**: success PR in `runPipelineFromImplementation` (`createPullRequest`); gate PRs in `pushAndOpenGatePr` (find → update, else create draft). A resumed run previously called `createPullRequest` even with a Draft PR open (GitHub 422) — fixed by AC-16.
- **Comment-command registration**: `handleIssueComment` in `routes/webhooks.ts` (bot guard → action → PR check → `startsWith` command match); permission via `checkReviewPermission`, kill switch via `config.ENABLE_PIPELINE_TRIGGER`, delivery dedupe via `claimDelivery` earlier in the `/github` handler.
- **Tests locking these areas**: `run-agent-pipeline.use-case.test.ts` (asserts a normal success run never reads orchestration state and never calls `findOpenPullRequestByHead` — kept true by scoping the PR lookup to `isRetry`/`approveSpec` jobs), `github-issue-trigger.test.ts` (mocked `githubService` as `{}`), `webhook-routing.test.ts` / `github-webhook-routing.test.ts` (config mocks without `specGateLabel` — handled by `resolveSpecGateLabel`'s default), `orchestration-state.test.ts`.

## Unexpected / decisions
- **Only `NEEDS_CLARIFICATION` triggers Clarify.** A `DRAFT` spec that still has an unanswered BLOCKING question is *not* stopped by the orchestrator (AC-8 says `DRAFT` goes on "like before"; the implementation agent itself stops on it, 03d). It is stopped later at `/caf-approve-spec` (AC-14). Planner status `NEEDS_HUMAN` passes through unchanged for the same reason.
- **GitHub `issues` trigger now resumes an existing branch** (see A3). A ready label re-applied on a ticket whose branch exists and has no state file gets the pre-existing "no prior orchestration state found — nothing to resume" comment, as Linear does today, instead of failing on a push as before.
- **Re-triggering a ticket that is waiting for spec approval** (Linear back to Ready, label re-applied, `/caf-retry-pipeline`) is not covered by an AC: it answers with a "waiting for approval, use /caf-approve-spec" comment, runs nothing and spends no retry (test: "a retry trigger while the spec awaits approval...").
- **The approval commit contains only the `Status:` line**: the state file keeps `waitingFor: 'spec-approval'` through it (clearing it would add a second changed file to that commit). It is replaced by a later gate failure or removed by the success reset; if the job dies in between, a repeated `/caf-approve-spec` takes the AC-15 path (already APPROVED, no commit) and resumes.
- **AC-12 "use case"**: a bot comment or an under-privileged sender is dropped in the route (before any job exists), so there is no use-case code for it; evidence is the route tests. The use case's own guard is AC-13 (job for a PR that is not waiting).
- **Rejections update the run row**: like the existing retry rejections, "not waiting"/rejected approvals call `finalizePipelineRun(..., 'NEEDS_HUMAN')`; `recordPipelineStarted` has already reset that ticket's row to running at job start, so a rejected command on an old PR leaves its dashboard row `NEEDS_HUMAN`.
- **The spec Draft PR stays a Draft after the pipeline succeeds** (the success path updates its body but there is no port to mark it ready for review). Same for a gate Draft PR resumed via `/caf-retry-pipeline`, which used to 422 on `createPullRequest`.
- The Clarify push failure is non-fatal (reported in the comment; the next trigger starts the spec from scratch); the spec-PR step swallows GitHub errors the same way the gate-exhaustion PR does. A failure to read ticket comments on resume *throws* (BullMQ retry) rather than running the planner blind.
- Not verified against live services: Linear's `botActor` on `comments`, Linear webhook `labels`, and GitHub comment payloads are tested against fixtures only.
